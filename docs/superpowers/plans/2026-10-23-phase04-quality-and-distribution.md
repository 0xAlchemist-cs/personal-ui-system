# Phase 04 — 持续验证与按需分发（Conditional）

> 状态：**候选执行计划，未启动**。依赖 Phase 03 Gate；自动化与分发分成两条可以独立验收的轨道。总纲：[MASTER-PLAN.md](../MASTER-PLAN.md)。来源：[用户计划包](../../imports/personal-ui-system-plan-kit/README.md)。

## 0. 本阶段只解决重复发生的问题

目标：让高风险变更拥有可重复验证的证据，减少多项目复制的差错；如出现真实的多个消费者需求，再做版本化分发。

- 依据现有测试与业务风险选择工具，优先复用消费者已有 CI/浏览器设施。
- 规范来源：[Brief Schema](../../../briefs/ui-brief.schema.json)、[Token 契约](../../../design-system/tokens/README.md)、[资产生命周期](../../guides/asset-lifecycle.md)、[验收约定](../../../tests/README.md)，以及 [Phase 02](2026-10-23-showcase-v1.md) / [Phase 03](2026-10-23-phase03-consumer-pilot.md) 届时产出的实际验证证据。
- 不在本阶段重新定义 UI Brief 或设计 Token 值；不默认发布 npm、Registry 或开源 MCP。

## 1. 前置 Gate

- [ ] Gate 03 成功，有实际独立消费者与闭合快照复用证据。
- [ ] 列出当前需要每次重复执行、且失败后果明确的检查；区分可自动化与必须人工确认的项目。
- [ ] 若要启动分发轨道，先提供真实需求清单：至少两个明确消费者，或明确的对外发布目标。

## 2. 轨道 A：可重复的质量门禁

### Task A1 — 把既有静态检查做成脚本和 CI

- [ ] 引入可固定版本的校验依赖，完成**完整的** JSON Schema Draft 2020-12 校验（而非只人工检查字段）；验证 YAML 解析、Token 引用/循环/非法预设覆盖与相对链接。
- [ ] 复用 Phase 02 应用的 TypeScript、Lint、Vitest 和构建脚本；CI 从干净环境安装，版本与锁文件一致。
- [ ] CI 出错时准确标记失败；不使用容错或忽略失败使构建假绿。

**证据：** 本地可重复命令、失败样例、CI 运行链接/日志以及真实环境约束。

### Task A2 — 浏览器冒烟与视觉回归

- [ ] 针对最关键用户旅程引入少量高价值浏览器测试；先验证可观察结果，不追求大量重复断言。
- [ ] 若确有可重复视觉回归需求，固定 OS/浏览器版本/字体/视口/数据/时区/缩放，再建立基线；基线初次建立及变更需人工审查。
- [ ] 对不稳定截图识别动态来源；禁止直接更新快照以压制真实差异。

**证据：** 浏览器测试报告、复现实验参数、已知波动边界。仅当启用视觉回归时，提供首批人工核准的基线；未启用时记录原因，不以缺少可选基线判定任务失败。

### Task A3 — 完成质量门禁收口

- [ ] 分辨机器能判定的项目与人工 UX 审查；维护失败修复、基线审核与异常升级路径。
- [ ] 将适用检查纳入必要的 PR/发布过程，但不强制无关消费者安装 Showcase 的全部工具。

**质量轨道完成：** 真实 CI 能在干净环境复现有效检查；关键用户旅程有可检验输出；视觉基线（如启用）有人审查。

## 3. 轨道 B：分发（达到触发条件才实施）

### Task B1 — 用实际消费者需求决策分发方式

选择最简单、长期维护成本最低的方案：

1. 无高频更新、消费者少：继续使用固定提交的闭合快照。
2. 以源码组件复制和改造为主：评估 Registry，明确技术栈限制。
3. 存在稳定版本化运行时组件、重复升级成本：评估 npm 包。

如没有足够证据，明确记录为 **Not needed**，不是“未完成”。禁止因组件库名义而强行发布。

### Task B2 — 仅对被选方案做最小实现与试用

- [ ] 固定版本与兼容性说明；将第三方许可证和授权边界纳入分发检查。
- [ ] 在真实消费者中验证安装、升级与回退，并观察有没有破坏性变化。
- [ ] 对未充分验证的组件保持 `draft`/`validated`，不默认 `approved`。

**分发轨道完成：** 明确选择“不分发”或经真实消费者验证了一种最小分发途径；不需要同时支持三种方式。

## 4. 每个任务的小 Prompt（按条件使用）

### P04-A1｜持续静态校验
> 请执行本文件 **Task A1**。仅把已经存在且值得重复运行的 Brief Schema、Token、链接和 Showcase 构建检查转为可复现脚本/CI。使用锁定依赖与负面测试样例，不改 Brief 或 Token 的业务语义。报告干净环境真实测试结果与失败证据。

### P04-A2｜浏览器与视觉基线
> 请执行本文件 **Task A2**。选择 Phase 02/03 实际高风险旅程，补最少的浏览器端验证；如确认启用视觉回归，再固定环境并建立需人工批准的截图基线，未启用时记录原因。不要建立无依据的大规模快照，也不要自动批准截图差异。报告环境、覆盖、结果和不稳定因素。

### P04-A3｜质量收口
> 请执行本文件 **Task A3**。检查 CI、浏览器、视觉检查各自已验证范围；把失败处理和人工验收职责写入适当的唯一来源文档。只根据已执行证据更新阶段状态，列出继续不适合自动化的检查。

### P04-B1｜分发必要性评估
> 请执行本文件 **Task B1**。读取 Phase 03 的消费者实测记录，确认是否有至少两个明确消费者或正式发布目标。比较固定快照、Registry 和包的成本；如需求不足，明确建议维持快照，不启动发布工程。输出可审核的决策依据，不写分发代码。

### P04-B2｜单方案试点
> 请执行本文件 **Task B2**（仅在 B1 决定需要分发后）。只实现 B1 选定的一种方案，完成固定版本、消费者安装/升级/回滚与许可证检查。不要顺手搭建另外两种分发方式。用真实消费证据决定是否达到轨道完成条件。
