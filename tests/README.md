# 质量与验收

本文件是 PR 与候选发布的唯一验收约定；[PR 模板](../.github/PULL_REQUEST_TEMPLATE.md)、工具说明只引用本规则，不另维护一套门槛。规则核对日期：2026-10-24；当前工作流与已验证范围依据 [A1](../docs/records/2026-10-24-p04-a1-quality-checks.md)、[A2](../docs/records/2026-10-24-p04-a2-browser-smoke.md)。阶段状态仍以 [路线图](../docs/roadmap.md) 为准。

## PR 与候选发布前核对

作者提供变更范围、待交付的完整源码 SHA、CI 运行链接和适用人工证据；合并或交付前由执行者/维护者按下表核对。源码变化后，旧 SHA 的成功不能代替新提交的检查。PR 若检查的是合并提交，须记录实际受检 SHA 及其对应的 head/base；候选发布须有精确候选 SHA 的成功结果。

| 检查对象 | 机器可以判定 | 人工仍需判断 / 适用范围 |
| --- | --- | --- |
| 知识契约 | `Knowledge contracts` job：JSON/YAML、完整 Brief Schema、预设一致性、Token 图、本地链接与 39 项正负例 | 规则和文案是否符合真实需求；链接检查不覆盖外网可达性或标题锚点 |
| Showcase 工程 | `Showcase checks and builds` job：类型、Lint、78 项应用测试、应用与 Storybook 构建 | 构建可用不等于页面可用；既有包体警告按原报告记录 |
| Showcase 关键旅程 | 同一 Showcase job：生产构建下三个视口共 11 项 Chromium 行为、焦点和布局边界检查，零重试 | 只覆盖所列旅程；不代表全站纯键盘、读屏、多浏览器、真实移动设备或 200% 缩放全部通过 |
| UI / UX | 现有断言与诊断截图提供辅助证据，无像素比较基线 | UI 变更人工查看受影响页面/Story、状态、375/768/1440px 布局、焦点/键盘与可读性；涉及缩放、对比度或语义时补相应检查，记录环境、结果与截图/问题 |
| 独立消费者 | 使用消费者既有且适用的安装、类型、Lint、测试、构建或浏览器设施 | 按自己的技术栈和风险验收快照及本地修改；不迁移框架，不为本约定安装 Showcase 全部工具 |

本仓库所有 PR 在合并前、候选版本在交付前，均核对 [Quality workflow](../.github/workflows/quality.yml) 的上述两个 job 对适用受检 SHA 都为 `success`；失败、取消、跳过、未运行均不算通过。文档修改也接受现有 workflow，但无需为可逆文案修改新增测试或重做无关浏览器/人工验收。UI 变更需附上述人工结果；不适用项写明原因，不勾选成通过。消费者只执行适用检查，记录来源 SHA、自己的受检版本与覆盖范围。

这是执行约定和复核入口。2026-10-24 核对时分支保护未启用、required contexts 为空；PR 模板与 workflow 的存在不能强制阻止合并。本任务不配置平台保护，也不新增例行修复的审批前置条件。

## 失败修复与异常升级

1. **先保留事实。** 记录受检 SHA、run/job 链接、命令、退出码、环境与原始失败。浏览器步骤实际运行后，CI 上传 HTML/JSON 报告及可用的失败截图、trace，artifact 保留 **7 天**；在到期前将需长期追踪的报告、截图/trace及关联日志保存为仓库相对路径附件或稳定链接，并记录日期、范围和来源。若检查在安装阶段就失败或运行被取消，可能没有浏览器附件，须明确写“未生成”，不能补称浏览器通过。
2. **区分原因。** 依锁文件和固定环境复现，排查安装/下载、权限、端口、runner 与字体等环境差异，再检查产品、测试或知识契约。环境错误同样是未通过；注明依据后可重跑同一 SHA。保留原失败和重跑结果，不能只挑一次绿灯；重复波动须分析动态来源，不能靠增加重试或放宽断言掩盖问题。
3. **最小修复并复核。** 在已授权范围内修复代码、测试或文档，复测受影响项；修改后让待交付 SHA 的两个 job 重新成功，并更新相关人工证据。保留失败→原因→修复→复测关联；不得删除有效检查、忽略退出码、降低可见性要求或更新快照来消除失败。
4. **遇到边界再升级。** 无法稳定复现、重复失败或环境权限/runner 故障阻碍检查时，将失败与复现证据交给维护者；需求/Token/Brief 契约变更或真实 UX 取舍若不能由现有授权和规则确定方案，再交维护者/用户决策。未来视觉基线仍需下节所述人工核准，超出已有授权的不可逆操作也须另行决策。继续完成不受影响的已授权工作；例行修复不因尚无新审批而停下。未解决的关键失败不能标为验收通过，非阻断限制需说明影响与后续安排。

## 视觉基线与人工审阅

**当前未启用像素比较基线，这是 A2 的有依据选择，不是待补的失败项。** Windows 人工验收、包内 Chromium 与 Ubuntu runner 的环境/实际中文字形不同；字体未固定，也没有经人工核准的 Linux 参考图。现有截图用于诊断或人工验收，`updateSnapshots: 'none'`，没有 `toHaveScreenshot`；不把历史图片转称基线。

只有确认存在可重复视觉回归需求时才另行启用：先固定 OS 镜像、浏览器版本、实际字体、视口/DPR、缩放、数据、语言、时区和动态效果，记录源码 SHA；识别并控制动画、异步内容等差异来源。首次建立及每次修改基线都需人工审阅实际图片与差异，记录审核人、日期、理由、环境和受检 SHA 后才采用。差异出现时先判断真实缺陷与环境变化，不自动批准或直接更新图片。

UI 变更的人工记录可使用 [人工验收模板](visual-review-template.md) 和 [验收提示词](../prompts/visual-qa.md)；区分通过、失败、未执行和不适用。自动检查不代替审美、层级、密度、文案、完整键盘流程和辅助技术判断，也不提升资产成熟度。
